## Gotchas
- ttrput manifests can be SILENTLY dropped: TTRField.parse (src/dylan/formula/ttr_field.py:59-72) accepts manifest=None when Formula.create returns None — only a DEBUG-level log (formula.py:226). The 2026/2015 grammars' quantifier terms `x1==(QUANT, r.head, r):e` (lexical-actions.txt:62,138,154) all hit this: every/the/my/your semantics are quietly broken, not failing.
- Lexical freshening is a NO-OP in the live parser: TTRFreshPut passes the parser Context (ttr_fresh_put.py:47); resolve_freshen_tree (ttr_formula.py:29-36) only unwraps ParserTuple/DAGInductionTuple, and TTRRecordType.freshen_vars_tree returns clone() for non-Tree input (ttr_record_type.py:386-388). Consequence: two NPs sharing lexicon variable names collapse under asymmetric_merge — 'a man likes a woman' loses 'woman' entirely (p3==obj(e1,x) where x is the man); 'john likes mary' loses 'mary'. Any MLTT translation of final records inherits this corruption.
- det_quant lives inside a //*...*// deprecated block comment (resources/2026-english-ttr/lexical-actions.txt:53-79) and only works because a Python-port-only shim resurrects templates referenced by lexicon.txt (_lexicon_recover_missing_templates, src/dylan/action/lexicon.py:801-818). Java DyLan would not load it. Do not 'clean up' the comment or the shim without deciding what the/every should do.
- get_final_semantics hard-raises TypeError unless evaluate() returns exactly a TTRRecordType (dag_parser.py:164-165). DisjunctiveType (produced for unfixed-merge ambiguity at tree.py:559) fails this gate because its evaluate() returns self (disjunctive_type.py:24-28, Java MSCST unported) — sentences triggering two-tree merge_unfixed will crash final extraction, not degrade.
- Field order in TTRRecordType is dependency-sorted at insertion (add(), ttr_record_type.py:234-261), NOT source order: parsing 'R^[r:R | x1==...:e | head==x1:e]' yields [x1 : e|head==x1 : e|r : R]. Use parse_strict_field_order (:122) when order matters. Equality is order-insensitive (:590-602) but there are TWO __eq__ definitions in the class body — the second (:1530-1538, dataclass-field list comparison, MetaTTRRecordType NotImplemented hook) is the one that wins.
- asymmetric_merge REPLACES same-label fields (remove-then-add, ttr_record_type.py:323-341): the argument NP's head==x1:e is overwritten by the verb's head==e1:es at the root merge; 'head' collisions are by design, other label collisions are how the freshening bug corrupts records.
- Case-sensitivity traps in parsing: 'R'/'R1' are Variables/binders and 'R1.head' is a TTRAbsolutePath (ttr_path.py:22 ^R\d*$), while 'r.head' is a TTRRelativePath; 'X'-'Z' are lexical rule metavariables (formula.py:57), 'S'-'U' freshput metas (formula.py:54), 'U','U1' FormulaMetavariable (formula.py:53), 'REC*' MetaTTRRecordType (formula.py:52). A DSType metavar is [V-Z][0-9]* (dstype.py:18) — 'R' is NOT one, which is why 'r:R' becomes manifest Variable R rather than a type.
- epsilon(...)/iota(...)/tau(...) functor-form strings parse as plain PredicateArgumentFormula, never as EpsilonTerm — EpsilonTerm has no parse() and is constructed nowhere except a dead isinstance-rebuild branch in induction_semantics.py:82-87. String-matching vestiges: get_restrictor_field startswith check (ttr_record_type.py:1166-1171), em_learner/evaluation.py:67-89.
- Removing epsilon_term.py appears safe for parsing but the import at induction_semantics.py:44 is inside bind_metavar_path_domains, which tree.py imports on EVERY context-ful get_maximal_semantics call (tree.py:358) — the function body (and its EpsilonTerm import) only executes when a gold target exists, so plain parsing survives, EM induction ImportErrors.
- Lexicon.lookup caps entries per word at top_n=3 (lexicon.py:362-365, constructor default _top_n=3) — words with >3 templates silently lose entries.
- The Elimination rule's beta-reduce effect is DSType-driven and duck-typed (beta_reduce.py:28-35), so it is NOT a TTR chokepoint; the real chokepoints are Tree._max_sem_at (tree.py:476-483 raises TypeError for non-TTR functors) and TTRFormula.conjoin (ttr_formula.py:68-71).
- The 2026-english-ttr grammar resolves through the dynamicsyntax.resources package mapping to the repo resources/ directory (src/dynamicsyntax/_session.py:31-42); the wheel-bundled grammars dir contains only 2015-english-ttr.
- Underspecified formulae are injected at EVALUATION time, not parse time: nodes lacking Fo get TTR templates from the static type map (underspecified_type_map.py:24-38) inside get_maximal_semantics (tree.py:331-352 with context, :397-428 without), including the ?Ex.fo(x) e>t special case (tree.py:420-425). Final semantics therefore differs from what the tree literally carries.
- TTRRecordType.parse of a field whose ':'-rhs is not a valid DSType reinterprets the rhs as a manifest formula (ttr_field.py:83-87) — an MLTT type expression on the rhs would be mis-parsed, not rejected.

## Answers

### q1
The pipeline is Formula-generic at the node/label/action layer but hard-wired to the TTR class family at (a) grammar parse, (b) tree evaluation, (c) final extraction. A parallel MLTT hierarchy (Pi, Sigma, Universe, proof terms) would have to either subclass TTRFormula and implement its combination protocol, or fork ~3 functions. Complete list of isinstance/type gates on the live parse path (abs paths under src/dylan unless noted):

GRAMMAR LOAD / STRING PARSE:
- formula/formula.py:189 `isinstance(body, TTRFormula)` — `R…^body` binder becomes TTRLambdaAbstract only if body is TTRFormula, else FOLLambdaAbstract (formula.py:191-193). ### q2
A post-hoc TTRRecordType→MLTT translation is the far cheaper option and is highly feasible, because the final object is a closed, small data shape. What a final TTRRecordType carries: an ORDERED list of TTRField(label: TTRLabel, ds_type: DSType|None, manifest_type: Formula|None) (ttr_record_type.py:88-101, ttr_field.py:42-48); order is dependency-sorted at insert time (add(), ttr_record_type.py:234-261); the dependency graph is recoverable via get_parents/get_dependents/depends_on (ttr_record_type.py:1031-1077, ttr_field.py:163-179); the head is a distinguished field labelled `head` whose manifest is a Variable naming another field (head() :558, get_head_field() :295-306, has_manifest_content() :544-552).

EMPIRICAL field/value shape inventory, collected by running .venv/bin/python parses of 8 sentences with grammar 2026-english-ttr (every/a/the man arrives, john arrives, john likes mary/the woman, a/every man likes a woman, does john arrive) — the COMPLETE set of shapes observed in final semantics:

3. (TTRLabel, e, Variable) — head pointer inside restrictor sub-records, `head==x : e`.

5. (TTRLabel, es, Variable) — top-level head pointer, `head==e1 : es`.
6. (TTRLabel, t, PredicateArgumentFormula) — proof/proposition fields, `p==man(x) : t`, `p1==pres(e1) : t`, `p2==subj(e1, x1) : t`, `p3==obj(e1, x) : t`, `p0==question(e1) : t` (polar question, tree.py:512-515).

Lambda abstractions exist only on intermediate functor nodes (TTRLambdaAbstract, binders R/R1/R2 over records, bodies are records or ++-infix chains). If translating final semantics only, you never see them; each of the 7 shapes maps naturally: unmanifest x:e → Sigma-bound variable x:Entity; x==a:e → singleton/definitional binding; p==pred(args):t → proof field of El(pred args) with dependencies given by argument Variables naming earlier labels; nested r:[...] → nested Sigma record; head==l → distinguished projection annotation.
